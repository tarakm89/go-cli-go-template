## Problem

What is wrong today, for whom, and what does it cost? Concrete over abstract:
name the failure someone actually hit.

## Goals

What this must achieve. Keep it short — three or four bullets. Anything longer
is usually two specs.

## Non-goals

What this deliberately does not address. This section prevents more argument
than any other.

## Proposal

The behaviour you want, in enough detail to build from. Interfaces in domain
types, not in library types. Where a diagram helps, use one — the site renders
Mermaid.

## Acceptance criteria

How we will know it works, written so each line can become a test. If you
cannot write these, the problem is not understood yet.

- [ ] Given …, when …, then …
- [ ] …

## Alternatives considered

What else was on the table and why it lost. A rejected option with a reason is
worth more than a list of what was chosen.

## Risks and costs

What this makes harder, slower or more fragile. Every design has a bill; say
what it is.
